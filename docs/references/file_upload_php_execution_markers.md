# PHP execution markers for file-upload verification

These deliberately small PHP fixtures support authorized file-upload verification. They are not
line-oriented dictionaries, are never offered by the wizard, and are not composed into generated
filenames.

## Why the marker is encoded in the fixture

Both fixtures execute this PHP expression:

```php
echo base64_decode("cGhwX2Z1bmNpb25h");
```

The decoded response contains `php_funciona`, but that text does not occur literally inside either
fixture. Consequently, matching `php_funciona` distinguishes PHP execution from a server returning
the uploaded source as plain text.

## Included fixtures

| Fixture | Purpose |
|---|---|
| [`php_execution_marker.php`](../../fixtures/file_upload/php/php_execution_marker.php) | Emit only the stable execution marker. |
| [`php_execution_and_path_marker.php`](../../fixtures/file_upload/php/php_execution_and_path_marker.php) | Emit the marker and hexadecimal path diagnostics. |

The diagnostic fixture reports the basename, `__FILE__`, `realpath(__FILE__)`,
`SCRIPT_FILENAME`, `DOCUMENT_ROOT`, and `REQUEST_URI`. Hexadecimal output preserves otherwise
ambiguous bytes in stored filenames and filesystem paths.

## Matching with ffuf

After uploading one of the fixtures under an authorized test filename, a generated request-path
wordlist can be checked with a stable response matcher:

```bash
ffuf -w output/file_upload_request_path_variants.txt \
  -u 'https://example.test/uploads/FUZZ' \
  -mr 'php_funciona'
```

A match demonstrates that the response was generated by executing the PHP expression, rather than
merely finding the encoded source string. It does not by itself prove that every request reached
the same backend or bypassed an intermediary cache, so verify the matching response when that
distinction matters.

The path diagnostic output can disclose server filesystem layout. Use it only in an authorized
environment and remove uploaded fixtures after the test.
